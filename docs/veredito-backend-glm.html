Critérios eliminatórios

  • ✓Fastify executa a API e o TypeScript compila: npm ci, typecheck, build e test terminaram com exit 0.
  • ✓O SQLite em arquivo persiste estado após reinício. Usuário criado por signup, contatos e transferências sobreviveram a seis reinícios, um deles com kill -9, e o seed não foi reaplicado.
  • ✓CQRS tem caminhos distintos. POST /v1/transfers chega em transfers/commands/request-transfer.ts e GET /v1/accounts/me/balance chega em accounts/queries/get-balance.ts.
  • ✓A Saga usa commits locais separados, guarda o progresso em transfers.saga_step e na tabela jobs, e teve compensação e recuperação demonstradas por execução.
  • ✓Autenticação e isolamento por usuário funcionam, incluindo logout com corpo JSON vazio e sessão expirada no banco.
  • ✓Nenhum saldo negativo, débito ou crédito duplicado. A soma de saldos com o valor em trânsito ficou em 125000 centavos em todos os cenários.

Achados, do mais grave ao mais leve

JSON malformado no corpo responde 500 em todas as rotas POST

A rota de autenticação registra um parser de application/json que transforma corpo vazio em {}. Como ele é registrado no escopo raiz, vale para todas as rotas. Quando o JSON é inválido, o parser repassa o SyntaxError cru, sem código Fastify nem statusCode, e o mapeador de erros o trata como falha interna. O comentário no código diz que JSON inválido continua 400. A resposta não vaza detalhes, e o stack fica só no log.

Severidade média · src/modules/auth/routes.ts:21 e src/shared/errors.ts:118 · reproduzir: POST /v1/auth/signin com Content-Type: application/json e corpo {"email":

O seed reutiliza um único hash para as três contas demo

Alice, Bruno e Carla têm o mesmo password_hash, com o mesmo salt, porque o seed calcula o hash uma vez só. Usuários criados por signup recebem salt próprio, então o critério de hash com salt se mantém.

Severidade baixa · src/db/seed.ts:36

A validação do corpo roda antes da autenticação

Uma requisição sem sessão e com corpo inválido recebe 400 em vez de 401. Com corpo válido, o 401 aparece como o contrato pede.

Severidade baixa · ordem do ciclo do Fastify (validação antes do preHandler)

O OpenAPI não documenta o 403 de Origin

Nenhuma das cinco rotas POST lista a resposta 403 ORIGIN_NOT_ALLOWED, que a execução mostrou em mutações com Origin estranha.

Severidade baixa · openapi.json

Manutenção e documentação

O arquivo de rascunho iso.tmp.mjs, um servidor Fastify de teste com 39 linhas, foi commitado no commit 7da145b e ficou na entrega, junto com a configuração de ferramenta em .serena/. A tabela de estados do README traz o erro de digitação "crédio". O /health usa o código SERVICE_UNAVAILABLE, que não está no catálogo do contrato.

Sem severidade funcional

Três ajustes prioritários

  1. No parser de JSON, devolver o erro de sintaxe com statusCode: 400, ou mapear SyntaxError para 400 VALIDATION_ERROR no mapeador de erros, e mover o parser para um local que deixe claro que ele vale para toda a API.
  2. Documentar no openapi.json a resposta 403 ORIGIN_NOT_ALLOWED das rotas de mutação.
  3. Remover iso.tmp.mjs e .serena/ do repositório e calcular um hash por usuário no seed.

Como reproduzir

A avaliação rodou numa cópia isolada do commit 3e85f6d. Instalação e verificação estática:

npm ci
npm run typecheck   # exit 0
npm run build       # exit 0
npm test            # 29 arquivos, 203 testes, exit 0

Os cenários de API usaram scripts externos do avaliador, escritos a partir do contrato, que não alteram o código avaliado. harness.mjs sobe node dist/server.js com um DATABASE_PATH temporário e controles de teste ligados, executa 71 checks de BE01 a BE11 com requisições HTTP reais, mata o processo com SIGKILL no cenário de crash e confere saldos e ledger direto no SQLite. probe.mjs e probe2.mjs testam signout e corpos inválidos. eval-be10-6.ts roda o subcaso de compensação com outras operações chamando o orquestrador direto, como a rubrica permite quando os dois modos de falha não podem ser combinados pela API.

Resultado bruto do harness: 68 checks passaram e 3 falharam, nenhum por defeito coberto pela rubrica. Dois esperavam ver "125000" no texto de saída de db:seed e db:reset; os comandos terminam com exit 0 e a soma foi confirmada no banco. O terceiro esperava hashes distintos no seed e aparece aqui como achado de severidade baixa. O defeito do JSON malformado foi encontrado pelas sondas.
