Critérios eliminatórios

  • ✓Fastify executa a API e o TypeScript compila: npm ci, typecheck, build e test terminaram com exit 0.
  • ✓O SQLite em arquivo persiste estado após reinício. Usuário criado por signup, contatos e transferências sobreviveram a quatro reinícios, e o seed não foi reaplicado.
  • ✓CQRS tem caminhos distintos. POST /v1/transfers chega em commands/request-transfer.ts e GET /v1/accounts/me/balance chega em accounts/queries/get-balance.ts.
  • ✓A Saga usa commits locais separados, guarda o progresso em transfers.saga_step e na tabela jobs, e teve compensação e recuperação demonstradas por execução.
  • ✓Autenticação e isolamento por usuário funcionam. O defeito do signout aparece só com uma combinação específica de cabeçalhos e não abre acesso a dados de outra conta. Por isso entrou como parcial em BE02, sem eliminar a entrega.
  • ✓Nenhum saldo negativo, débito ou crédito duplicado. A soma de saldos com o valor em trânsito ficou em 125000 centavos em todos os cenários.

Achados, do mais grave ao mais leve

Signout com JSON vazio responde 500 e mantém a sessão ativa

O hook preParsing do signout troca o corpo vazio por {}, mas o Content-Length continua 0. O Fastify lança FST_ERR_CTP_INVALID_CONTENT_LENGTH antes do handler, e o usuário fica logado. Esse é justamente o caso que o comentário do código diz tratar, e o contrato prevê um proxy repassando o cabeçalho.

Severidade média · src/modules/auth/routes.ts:54 · reproduzir: POST /v1/auth/signout com cookie válido, Content-Type: application/json, Content-Length: 0

Erros 4xx do Fastify fora do mapeamento viram 500

No log do caso acima, o erro chegou com statusCode: 400 e saiu como 500 INTERNAL_ERROR. O mapeador só reconhece alguns códigos FST_ERR_CTP_*, então outros erros de transporte do cliente aparecem como falha do servidor.

Severidade baixa · error handler em src/http/plugins/errors.ts

O seed reutiliza um único hash para as três contas demo

Alice, Bruno e Carla têm o mesmo password_hash, com o mesmo salt. Usuários criados por signup recebem salt próprio, então o critério de hash com salt se mantém. O efeito é só no seed.

Severidade baixa · src/db/seed.ts:56

O consumo do FAIL_CREDIT_ONCE fica fora da transação de compensação

A falha injetada é marcada como consumida numa transação e o estado COMPENSATING é gravado em outra. Se o processo morrer entre as duas, a retomada credita normalmente e a falha armada se perde. O próprio código documenta a janela, e ela afeta só o controle de teste.

Severidade baixa · src/modules/test-controls/fault-hooks.ts:58

A validação do corpo roda antes da autenticação

Uma requisição sem sessão e com corpo inválido recebe 400 em vez de 401. Com corpo válido, o 401 aparece como o contrato pede.

Severidade baixa · ordem do ciclo do Fastify (validação antes do preHandler)

Manutenção e documentação

Os controles de teste são ligados ao servidor por variáveis em globalThis, com 10 ocorrências fora dos testes. O insertCreatedTransfer de steps.ts repete o INSERT do comando. O RELATORIO.md fala em 30 arquivos de teste, e a execução mostrou 29, com os mesmos 132 testes. O mesmo relatório data os comandos finais em "~23:49 UTC", mas o arquivo foi salvo às 23:56 GMT+2 e o uso no OpenRouter termina perto de 23:58 GMT+2, então o horário está em GMT+2 com o fuso rotulado errado. O /health usa o código SERVICE_UNAVAILABLE, que não está no catálogo do contrato, mas o README declara isso.

Sem severidade funcional

Três ajustes prioritários

  1. Fazer o signout aceitar corpo vazio sem reescrever o stream (por exemplo, com um parser de conteúdo tolerante só nessa rota) e mapear no error handler qualquer erro do Fastify com statusCode 4xx para 400 VALIDATION_ERROR.
  2. Rever a política de testes só unitários. O defeito do signout existe apenas na camada HTTP, que essa política deixou sem cobertura. Alguns testes de rota com fastify.inject teriam pegado o problema. A decisão é do dono do projeto.
  3. Gravar o consumo do FAIL_CREDIT_ONCE na mesma transação do markCompensating e trocar o globalThis por injeção de dependência no buildApp.

Como reproduzir

A avaliação rodou numa cópia do projeto. Instalação e verificação estática:

npm ci
npm run typecheck   # exit 0
npm run build       # exit 0
npm test            # 29 arquivos, 132 testes, exit 0

Os cenários de API usaram três scripts externos que não alteram o código avaliado. harness.mjs sobe node dist/server.js com um DATABASE_PATH temporário e controles de teste ligados, executa os 71 checks de BE01 a BE11 com requisições HTTP reais, mata o processo com SIGKILL no cenário de crash e confere saldos e ledger direto no SQLite. probe.mjs isola o defeito do signout. eval-be10-6.ts roda o subcaso de compensação com outras operações chamando o orquestrador direto, como a rubrica permite quando os dois modos de falha não podem ser combinados pela API.

Resultado bruto do harness: 69 checks passaram e 2 falharam. Um deles é o signout. O outro foi um check do próprio avaliador, que esperava hashes distintos no seed; ele não faz parte da rubrica e aparece aqui só como achado de severidade baixa.
